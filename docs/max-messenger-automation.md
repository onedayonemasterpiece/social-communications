# MAX Web: детерминированная отправка в разные чаты

## Статус

Рабочий контур использует сохранённую авторизованную сессию из repository secret `MAX_SESSION` и управляет официальной веб-версией MAX через Playwright.

Поддержаны три операции:

- немедленная отправка текста;
- нативная отложенная отправка текста средствами MAX;
- публикация изображения с подписью и форматированными HTTPS-ссылками.

Целевой чат задаётся точным отображаемым названием. Поиск считается успешным только при единственном видимом точном совпадении; после открытия дополнительно проверяется заголовок чата. Нечёткий выбор первого похожего результата запрещён.

## Почему без LLM в контуре отправки

Для текущих пользовательских путей LLM не требуется. Элементы MAX имеют воспроизводимые роли, aria-label, текстовые названия и проверяемые состояния. Поэтому выбор чата, даты, времени, файла, текста и кнопки отправки выполняется только детерминированным кодом.

LLM допустима лишь как отдельный read-only диагностический контур после отказа селекторов:

1. основной сценарий завершается fail-closed до опасного клика;
2. формируется обрезанная и обезличенная DOM-сводка;
3. модель предлагает диагностическую гипотезу или новые кандидаты селекторов;
4. кандидаты проверяются отдельным тестом и только затем фиксируются в коде.

Если такой контур понадобится, предпочтительна Gemini Lite через существующий общий limiter. Модель не должна получать сессию, cookies, полный список чатов и не должна самостоятельно нажимать `Отправить`. Сейчас LLM и её лимиты в MAX-контур не подключены, потому что продуктового основания для этого нет.

## Командный контракт

JSON Schema: [`contracts/max-command.schema.json`](../contracts/max-command.schema.json).

Обязательные поля:

```json
{
  "version": 1,
  "requestId": "unique-idempotency-key",
  "chat": {
    "title": "Точное название чата"
  },
  "action": "text | schedule_text | rich_post",
  "text": "Текст сообщения"
}
```

`requestId` предназначен для будущего долговечного реестра команд. Текущий web-контур дополнительно проверяет фактическое состояние MAX и не повторяет найденный rich post или отложенное сообщение.

### Немедленный текст

```json
{
  "version": 1,
  "requestId": "message-20260807-001",
  "chat": { "title": "Тестовая группа" },
  "action": "text",
  "text": "Пример сообщения"
}
```

### Отложенный текст

```json
{
  "version": 1,
  "requestId": "scheduled-20260808-1100",
  "chat": { "title": "Тестовая группа" },
  "action": "schedule_text",
  "text": "Тест отложенной отправки",
  "scheduleAt": "2026-08-08T11:00:00+02:00",
  "timeZone": "Europe/Kaliningrad"
}
```

Сценарий:

1. открывает нужный чат;
2. проверяет раздел `Отложенные сообщения`, чтобы не создать дубликат;
3. вводит текст;
4. открывает контекстное меню кнопки отправки;
5. выбирает `Отправить позже`;
6. детерминированно задаёт месяц, день, часы и минуты;
7. сверяет доступное имя подтверждающей кнопки, включая целевое время;
8. подтверждает;
9. повторно открывает список отложенных сообщений и проверяет текст вместе со временем.

### Изображение, текст и форматированные ссылки

```json
{
  "version": 1,
  "requestId": "rich-post-20260807-001",
  "chat": { "title": "Тестовая группа" },
  "action": "rich_post",
  "text": "Текст публикации",
  "image": {
    "path": "generated/max-test-post.png"
  },
  "links": [
    {
      "text": "Открыть «Полюбить Калининград»",
      "url": "https://kenigevents.ru/"
    }
  ]
}
```

Ссылка вставляется не как открытый URL, а как HTML-якорь через браузерный Clipboard API. Перед отправкой код проверяет, что Lexical-композер MAX действительно содержит `<a>` с точным текстом и каноническим `href`. После отправки отдельный свежий browser context проверяет, что один и тот же контейнер сообщения содержит:

- ожидаемый текст;
- изображение;
- ссылку с ожидаемым видимым текстом;
- точный HTTPS `href`.

Повторный запуск той же команды сначала выполняет эту строгую проверку и завершается `already_present`, не создавая дубль.

### Только проверка без отправки

Для безопасной повторной верификации существующего rich post или отложенного сообщения используется:

```json
{
  "verifyOnly": true
}
```

При `verifyOnly=true` никакой сценарий отправки не запускается. Результат — `verified_existing` либо fail-closed `not_found`.

## GitHub Actions

Основной workflow: [`.github/workflows/max-send.yml`](../.github/workflows/max-send.yml).

Ручной производственный запуск:

1. `Actions → MAX deterministic sender → Run workflow`;
2. передать полный command JSON;
3. оставить `capture_evidence=false`, если визуальная диагностика не нужна.

Push-trigger по `.github/max-live-command.json` оставлен для воспроизводимых тестов. В рабочей оркестрации предпочтителен `workflow_dispatch` или вызов через Actions API с неизменяемым command envelope.

## Безопасность и fail-closed правила

- используется только repository secret `MAX_SESSION`;
- значение сессии не печатается и не попадает в артефакты;
- чат выбирается только по одному точному совпадению;
- ссылки разрешены только по HTTPS;
- текст ограничен 4000 символами;
- тестовое изображение ограничено 20 MiB;
- время должно быть не менее чем на минуту в будущем;
- перед commit-point проверяются композер, форматированные ссылки, изображение и доступное имя кнопки;
- после commit-point выполняется независимая проверка фактического результата;
- при неоднозначности или изменении интерфейса действие не продолжается автоматически;
- параллельные отправки сериализуются concurrency-группой workflow.

## Артефакты и приватность

При включённом evidence сохраняется только правая часть интерфейса текущего чата и ограниченная DOM-сводка. Левая панель со списком чатов не попадает в скриншот. Срок хранения GitHub Actions artifact — один день.

После анализа artifact удаляется workflow `MAX artifact cleanup`. Производственный режим не должен создавать evidence без явной диагностической необходимости.

## Подтверждённые live-тесты

### Нативная отложенная отправка

В `Тестовая группа` создано отложенное сообщение:

- дата: 8 августа 2026 года;
- время: 11:00;
- часовой пояс: `Europe/Kaliningrad`;
- UI-подтверждение перед commit-point: `Отправить завтра в 11:00`;
- после commit-point сообщение присутствовало в разделе `Отложенные сообщения` с меткой `Завтра` и временем `11:00`.

### Rich post

В `Тестовая группа` опубликован один пост, содержащий:

- сгенерированное тестовое изображение 640×360;
- текст `Тест публикации с изображением и форматированной ссылкой.`;
- форматированную ссылку `Открыть «Полюбить Калининград»`;
- `href=https://kenigevents.ru/`.

Первоначальная проверка дала ложный отрицательный результат из-за переноса текста внутри контейнера сообщения, хотя пост был отправлен. После этого добавлен независимый структурный verifier. Повторный запуск нашёл ровно один контейнер с текстом, изображением и точным `href` и не создал дубликат.

## Следующие производственные усиления

Текущий контур уже выполняет пользовательские операции. Перед массовой оркестрацией полезно добавить:

- долговечный idempotency ledger по `requestId` вне GitHub artifact;
- реестр логических chat keys с приватным стабильным fingerprint маршрута;
- загрузку медиа по подписанному URL с проверкой MIME, размера и SHA-256;
- отдельные receipts для `accepted`, `scheduled`, `sent`, `verified`;
- мониторинг срока действия `MAX_SESSION` и безопасное обновление сессии.
