# MAX Web: безопасная отправка в разные чаты

## Назначение и текущий статус

Контур использует сохранённую авторизованную сессию из repository secret `MAX_SESSION` и управляет официальной веб-версией MAX через Playwright.

Канонический исполнитель поддерживает:

- текст;
- публикацию с изображением, подписью и форматированными HTTPS-ссылками;
- нативную отложенную отправку;
- подготовку сообщения в `Отложенных сообщениях` без доставки;
- немедленную отправку через двухфазный путь `создать отложенное → проверить → Отправить сейчас`.

Главный workflow: [`.github/workflows/max-send.yml`](../.github/workflows/max-send.yml). Командный контракт: [`contracts/max-command.schema.json`](../contracts/max-command.schema.json).

## Архитектурный принцип: LLM планирует, детерминированный код исполняет

Пользователь может поставить задачу естественным языком и неточно назвать чат: например, вспомнить только часть названия или допустить опечатку. Поэтому система разделена на два контура.

### 1. Семантический планировщик

Планировщик — текущий ассистент либо, в автономном режиме, отдельная LLM — извлекает:

- предполагаемый адресат;
- тип адресата: личный чат, группа, канал или бот;
- текст и форматирование;
- изображение;
- желаемое время;
- требование `отправить`, `отложить` или `оставить на проверку`.

Планировщик может использовать контекст разговора. Например, после фразы пользователя «я создал чат “Тестовая группа”» дальнейшее сокращение «в тестовую» не должно терять уже установленный точный адресат.

### 2. Детерминированный исполнитель

Исполнитель получает нормализованный JSON и только после этого управляет браузером. Он:

- не просит LLM выбирать DOM-элемент;
- не разрешает модели нажимать `Отправить`;
- не выбирает первый похожий результат;
- завершает работу fail-closed при неоднозначности;
- проверяет открытый заголовок чата до любого ввода;
- независимо проверяет результат после commit-point.

LLM может предложить кандидат адресата или исправленный поисковый запрос, но окончательное соответствие подтверждает только детерминированный код.

## Разрешение неточного названия адресата

Команда version 2 поддерживает три способа задать адресата:

```json
{
  "destination": {
    "key": "test-group"
  }
}
```

```json
{
  "destination": {
    "exactTitle": "Тестовая группа",
    "kind": "group"
  }
}
```

```json
{
  "destination": {
    "query": "тестовая група",
    "kind": "group"
  }
}
```

Приоритет разрешения:

1. стабильный `key` из приватного реестра;
2. точное название;
3. приватный alias;
4. детерминированный поиск по неточному запросу;
5. остановка и уточнение, если единственного сильного кандидата нет.

### Приватный реестр адресатов

Для регулярно используемых чатов рекомендуется repository secret `MAX_DESTINATIONS_JSON`:

```json
{
  "destinations": [
    {
      "key": "test-group",
      "title": "Тестовая группа",
      "kind": "group",
      "aliases": [
        "тестовая група",
        "тестовая группа в max",
        "тестовый чат"
      ]
    }
  ]
}
```

Реестр не хранится в публичном Git. Команда содержит только логический `key`, а точное название и aliases остаются в secret.

### Детерминированный fuzzy-поиск

Если реестра нет, исполнитель:

1. ищет исходную фразу;
2. при слабом результате создаёт ограниченный набор безопасных prefix-вариантов — например, `тестовая група` → `тестовая груп`;
3. оценивает заголовки отдельно от качества встроенного поиска MAX;
4. принимает только кандидата, прошедшего минимальный score и отрыв от второго места;
5. после клика проверяет заголовок открытого чата.

Это важно: живой поиск по фразе `тестовая` показал одновременно `Тестовая`, `Тестовая группа`, `Тестовая среда для розыгрыша` и другие результаты. Такая фраза действительно неоднозначна, поэтому автоматическая отправка была остановлена до открытия композера. Запрос с опечаткой `тестовая група` был разрешён через поисковый prefix `тестовая груп` в точный чат `Тестовая группа`.

Если кандидат неочевиден, планировщик должен использовать контекст либо задать пользователю одно уточнение. Ослаблять пороги и выбирать «наиболее похожий» чат нельзя.

## Невидимая для получателя подготовка

Для `delivery.mode=send_now` прямое нажатие обычной кнопки отправки запрещено. Используется двухфазный commit:

1. содержимое полностью проверяется до открытия целевого чата;
2. адресат разрешается и проверяется;
3. исполнитель проверяет, не опубликован ли уже тот же материал;
4. готовый текст вставляется одной clipboard-операцией, без последовательного набора символов;
5. изображение и форматированные ссылки проверяются в композере;
6. сообщение создаётся как нативное отложенное на parking-time в будущем;
7. оно заново находится в разделе `Отложенные сообщения` и структурно проверяется;
8. только после этого выполняется commit-point — пункт контекстного меню `Отправить сейчас`;
9. новый независимый browser context проверяет окончательное сообщение в чате.

До шага 8 получатель не получает сообщение и уведомление о сообщении. Отладка, изменение времени и редактирование должны выполняться над отложенным объектом через доступные команды MAX:

- `Отправить сейчас`;
- `Изменить время`;
- `Редактировать`;
- `Удалить`.

При ошибке до commit-point новый staged-объект удаляется best-effort. После commit-point слепой повтор запрещён: сначала выполняется независимая проверка результата.

### Граница доказанного

Двухфазный путь доказан для отсутствия промежуточного сообщения и промежуточного message-notification. Текст вставляется одной paste-операцией, поэтому окно возможного typing-status сведено к минимуму. Полное доказательство отсутствия индикатора «печатает…» требует наблюдения со второго аккаунта либо анализа протокольного события; такого теста пока нет. Поэтому система не заявляет неподтверждённую гарантию нулевого typing-indicator.

Практическое правило: LLM, редактура текста, получение изображения и проверка ссылок завершаются до открытия чата. В живом композере не должно быть итерационного сочинения текста.

## Командный контракт version 2

### Немедленная безопасная отправка текста

```json
{
  "version": 2,
  "requestId": "message-20260807-001",
  "destination": {
    "query": "тестовая група",
    "kind": "group"
  },
  "content": {
    "type": "text",
    "text": "Готовый текст сообщения"
  },
  "delivery": {
    "mode": "send_now",
    "timeZone": "Europe/Kaliningrad",
    "recipientInvisiblePreparation": true,
    "reuseExistingStage": true
  }
}
```

### Отправка в заданное время

```json
{
  "version": 2,
  "requestId": "scheduled-20260808-1100",
  "destination": {
    "key": "test-group"
  },
  "content": {
    "type": "text",
    "text": "Текст отложенного сообщения"
  },
  "delivery": {
    "mode": "schedule_at",
    "scheduleAt": "2026-08-08T11:00:00+02:00",
    "timeZone": "Europe/Kaliningrad",
    "recipientInvisiblePreparation": true
  }
}
```

### Подготовить, но не отправлять

```json
{
  "version": 2,
  "requestId": "draft-20260807-001",
  "destination": {
    "exactTitle": "Тестовая группа"
  },
  "content": {
    "type": "text",
    "text": "Материал для проверки"
  },
  "delivery": {
    "mode": "stage_only",
    "stageAt": "2026-09-01T12:00:00+02:00",
    "timeZone": "Europe/Kaliningrad",
    "recipientInvisiblePreparation": true
  }
}
```

### Изображение, подпись и форматированные ссылки

```json
{
  "version": 2,
  "requestId": "rich-post-20260807-001",
  "destination": {
    "key": "test-group"
  },
  "content": {
    "type": "rich_post",
    "text": "Текст публикации",
    "image": {
      "path": "generated/max-test-post.png"
    },
    "links": [
      {
        "text": "Открыть «Полюбить Калининград»",
        "url": "https://kenigevents.ru/"
      }
    ]
  },
  "delivery": {
    "mode": "send_now",
    "timeZone": "Europe/Kaliningrad",
    "recipientInvisiblePreparation": true
  }
}
```

Ссылка вставляется через HTML Clipboard API. До staging проверяются видимый текст и канонический `href`; после окончательной отправки свежий context требует, чтобы один message-container одновременно содержал подпись, изображение и точные ссылки.

### Только проверка

```json
{
  "verifyOnly": true
}
```

`verifyOnly` не создаёт staged-объект и не проходит commit-point. Результат: `verified_existing` либо fail-closed ошибка.

Legacy version 1 по-прежнему читается, но нормализуется в version 2. Даже старое действие `text` теперь идёт через staging, а не через прямую отправку.

## LLM и лимиты

В браузерном исполнительном контуре LLM не нужна и не должна использоваться. Для смыслового планирования адресата LLM полезна, потому что пользовательская формулировка может быть неполной.

Если потребуется автономный resolver вне текущего ассистента, рекомендуемая схема:

1. детерминированный поиск возвращает обезличенные кандидаты;
2. Gemini Lite через существующий общий limiter предлагает нормализованный intent и поисковые варианты;
3. модель не получает cookies, `MAX_SESSION`, полный DOM и тексты посторонних чатов;
4. её ответ не является разрешением на отправку;
5. детерминированный resolver повторно проверяет единственный точный адресат;
6. при остаточной неоднозначности требуется человек.

Предпочтительна Gemini Lite, а не Gemma, потому что здесь важнее устойчивое понимание коротких естественных формулировок и опечаток, чем локальное выполнение тяжёлой модели. Подключать её сейчас внутрь Playwright-path нет необходимости: задачи ставятся ассистенту, который уже выполняет semantic planning.

## Fail-closed и идемпотентность

- `MAX_SESSION` не печатается и не попадает в evidence;
- неоднозначный адресат блокирует выполнение до композера;
- текст ограничен 4000 символами;
- ссылки разрешены только по HTTPS;
- изображение проверяется до открытия чата и ограничено 20 MiB;
- содержимое вставляется атомарно;
- staged-объект должен быть найден ровно один раз;
- `Отправить сейчас` вызывается только после проверки staged-объекта;
- после commit-point результат проверяет новый browser context;
- повторный запуск сначала ищет уже опубликованный материал;
- параллельные команды сериализуются одной concurrency-группой.

`requestId` пока отражается в receipt, но долговечный ledger ещё не внедрён. Для массовой работы нужен отдельный private idempotency store.

## GitHub Actions, публичность и команды

Основной workflow принимает JSON через `workflow_dispatch` либо тестовый файл `.github/max-live-command.json`.

Поскольку репозиторий сейчас публичный, реальные тексты, названия закрытых чатов и URL изображений нельзя коммитить в `.github/max-live-command.json`. Для production нужен private command plane:

- workflow получает только непрозрачный `command_id`;
- зашифрованный payload хранится в приватном Supabase/YDB-контуре либо private repository/environment;
- payload читается однократно и после обработки помечается consumed;
- публичные Actions logs содержат только request ID, outcome и безопасные коды ошибок.

До внедрения private command plane публичный push-trigger предназначен только для безвредных тестов.

## Evidence и удаление артефактов

В production `capture_evidence=false`. При диагностике сохраняются только:

- обрезанная правая часть текущего чата;
- ограниченная DOM-сводка;
- JSON receipt без сессии.

Срок хранения — один день, но после анализа artifact удаляется workflow `MAX artifact cleanup`. Локальные копии также удаляются.

## Следующие усиления

- private destination registry и стабильные route fingerprints;
- private command queue вместо публичного JSON/push;
- долговечный idempotency ledger;
- signed media download с MIME, размером и SHA-256;
- отдельные durable receipts `accepted`, `staged`, `committed`, `verified`;
- монитор срока действия `MAX_SESSION`;
- тест со вторым аккаунтом на typing-indicator и фактическое уведомление;
- при необходимости — read-only Gemini Lite resolver через общий limiter.
