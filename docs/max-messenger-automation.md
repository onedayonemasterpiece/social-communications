# MAX Web: безопасная отправка в разные чаты

## Назначение и текущий статус

Контур использует сохранённую авторизованную сессию из repository secret `MAX_SESSION` и управляет официальной веб-версией MAX через Playwright.

Канонический исполнитель поддерживает:

- текст;
- публикацию с изображением, подписью и форматированными HTTPS-ссылками;
- нативную отправку в заданное время;
- подготовку сообщения в `Отложенных сообщениях` без доставки;
- немедленную отправку через двухфазный путь `создать отложенное → проверить → Отправить сейчас`;
- разрешение точных, неполных и опечатанных названий адресата;
- независимую проверку результата и защиту от дублей.

Главный workflow: [`.github/workflows/max-send.yml`](../.github/workflows/max-send.yml).

Командный контракт: [`contracts/max-command.schema.json`](../contracts/max-command.schema.json).

Live receipts: [`docs/evidence/max-live-test-report-2026-08-07.md`](evidence/max-live-test-report-2026-08-07.md).

## Архитектурный принцип: LLM планирует, детерминированный код исполняет

Пользователь может поставить задачу естественным языком и неточно назвать чат: вспомнить только часть названия, использовать разговорное имя или допустить опечатку. Поэтому система разделена на два контура.

### Семантический планировщик

Планировщик — текущий ассистент либо, в будущем, отдельная LLM — извлекает:

- предполагаемый адресат;
- тип адресата: личный чат, группа, канал или бот;
- текст и форматирование;
- изображение;
- желаемое время;
- режим: `отправить сейчас`, `отложить` или `подготовить без отправки`.

Планировщик обязан использовать контекст диалога. Например, после фразы пользователя «я создал чат “Тестовая группа”» дальнейшее сокращение «в тестовую» должно разрешаться прежде всего через уже установленный контекст, а не через слепой глобальный fuzzy-поиск.

### Детерминированный исполнитель

Исполнитель получает нормализованный JSON и только после этого управляет браузером. Он:

- не просит LLM выбирать DOM-элемент;
- не разрешает модели нажимать `Отправить`;
- не выбирает первый похожий результат;
- завершает работу fail-closed при неоднозначности;
- проверяет заголовок открытого чата до любого ввода;
- не сочиняет и не редактирует текст в живом композере;
- независимо проверяет результат после commit-point.

LLM может предложить нормализованный intent, точное имя или поисковые варианты, но окончательное разрешение адресата и commit выполняет только детерминированный код.

## Разрешение неточного названия адресата

Команда version 2 поддерживает три способа задать адресата.

### Стабильный logical key

```json
{
  "destination": {
    "key": "test-group"
  }
}
```

### Точное отображаемое название

```json
{
  "destination": {
    "exactTitle": "Тестовая группа",
    "kind": "group"
  }
}
```

### Неточный запрос

```json
{
  "destination": {
    "query": "тестовая група",
    "kind": "group"
  }
}
```

Приоритет разрешения:

1. точный адресат, уже установленный контекстом текущей задачи;
2. стабильный `key` из приватного реестра;
3. точное отображаемое название;
4. private alias;
5. детерминированный fuzzy-поиск;
6. одно уточнение пользователю, если единственного сильного кандидата нет.

Ослаблять пороги и выбирать «самый похожий» чат при остаточной неоднозначности запрещено.

### Приватный реестр адресатов

Для регулярно используемых чатов рекомендуется repository secret `MAX_DESTINATIONS_JSON`:

```json
{
  "destinations": [
    {
      "key": "test-group",
      "title": "Тестовая группа",
      "kind": "group",
      "aliases": [
        "тестовая група",
        "тестовая группа в max",
        "тестовый чат"
      ]
    }
  ]
}
```

Реестр не хранится в публичном Git. Команда содержит только logical key, а точное название и aliases остаются в secret.

### Детерминированный fuzzy-поиск

Если реестра и точного контекстного соответствия нет, исполнитель:

1. ищет исходную фразу;
2. при слабом результате создаёт ограниченный набор prefix-вариантов;
3. оценивает отображаемые заголовки отдельно от качества встроенного поиска MAX;
4. принимает только кандидата, прошедшего минимальный score и достаточный отрыв от второго места;
5. после клика проверяет заголовок уже открытого чата.

MAX search оказался prefix-friendly, но не всегда typo-tolerant. Поэтому запрос `тестовая група` безопасно расширяется, например, до `тестовая груп`, а окончательное соответствие всё равно считается относительно исходной фразы.

Live-проверка показала, что запрос `тестовая` действительно неоднозначен: в результатах были `Тестовая`, `Тестовая группа`, `Тестовая среда для розыгрыша` и другие варианты. Такой запрос был остановлен до открытия композера. Запрос `тестовая група` после prefix-expansion был разрешён в единственный сильный адресат `Тестовая группа`, затем дополнительно проверен заголовок открытого чата.

Failure receipts содержат только masked title hints и scores, а не полный список закрытых чатов.

## Двухфазная подготовка и отправка

Для `delivery.mode=send_now` прямое нажатие обычной кнопки отправки запрещено. Используется staged commit.

### Фаза 0. Подготовка вне чата

До открытия адресата исполнитель:

- валидирует размер и наличие изображения;
- проверяет HTTPS-ссылки;
- проверяет длину текста;
- получает уже готовую финальную редакцию;
- разрешает адресата.

LLM, редактура текста, получение изображения и выбор ссылок должны завершиться на этой фазе.

### Фаза 1. Создание staged-объекта

1. Исполнитель проверяет, не опубликован ли уже тот же материал.
2. Открывает единственный подтверждённый адресат.
3. Вставляет весь готовый текст одной clipboard-операцией, без посимвольного набора.
4. Для rich post загружает изображение и вставляет HTML-якоря.
5. Проверяет изображение, подпись, видимый текст ссылок и canonical href в композере.
6. Создаёт нативное отложенное сообщение на parking-time в будущем.
7. Открывает `Отложенные сообщения` и требует ровно один структурно совпадающий staged-объект.

До следующей фазы обычное сообщение в основной ленте чата не создаётся.

### Фаза 2. Commit

1. На проверенном staged-объекте открывается контекстное меню.
2. Выполняется `Отправить сейчас`.
3. Новый независимый browser context заново открывает точный адресат.
4. Финальный verifier требует ожидаемый текст; для rich post — текст, media и точные ссылки внутри одного message-container.

После commit-point слепой retry запрещён. Сначала всегда выполняется независимая проверка фактического результата.

### Ошибки до commit-point

Если новый staged-объект был создан, но проверка не прошла, исполнитель best-effort удаляет его через нативную команду `Удалить`. Композер очищается. Получатель не должен видеть незавершённый material как обычное сообщение.

### Редактирование и отладка staged-объекта

Live-интерфейс подтвердил команды:

- `Отправить сейчас`;
- `Изменить время`;
- `Редактировать`;
- `Скопировать текст`;
- `Выбрать`;
- `Удалить`.

Текущий автоматический path старается завершить всю редактуру до staging. Для более длинной работы используется `delivery.mode=stage_only`: сообщение создаётся и проверяется, но commit не выполняется. Следующая команда может найти тот же staged-объект и отправить его через `Отправить сейчас`.

## Граница доказанного по невидимости для получателя

Live-тест доказал следующее на стороне отправителя:

- до commit-point объект находился в `Отложенных сообщениях`;
- до commit-point он отсутствовал в основной ленте чата;
- после `Отправить сейчас` он появился в основной ленте;
- готовый текст вставлялся одной paste-операцией;
- повторные проверки не создавали дублей.

Важное ограничение: `Тестовая группа` во время теста содержала только владельца аккаунта. Поэтому пока **не доказаны наблюдением со второго аккаунта**:

- отсутствие recipient-side push/message-notification до commit-point;
- отсутствие кратковременного индикатора `печатает…` во время atomic paste;
- отсутствие иных recipient-side presence-сигналов.

Нативная модель `Отложенных сообщений` и отсутствие сообщения в основной ленте дают сильное основание ожидать, что message-notification до commit-point не возникает, но это остаётся выводом, а не завершённым двухсторонним тестом. Для строгой гарантии нужен второй тестовый аккаунт или второй участник группы с фиксацией уведомлений и typing indicator.

## Командный контракт version 2

### Безопасная немедленная отправка текста

```json
{
  "version": 2,
  "requestId": "message-20260807-001",
  "destination": {
    "query": "тестовая група",
    "kind": "group"
  },
  "content": {
    "type": "text",
    "text": "Готовый текст сообщения"
  },
  "delivery": {
    "mode": "send_now",
    "timeZone": "Europe/Kaliningrad",
    "recipientInvisiblePreparation": true,
    "reuseExistingStage": true
  }
}
```

### Отправка в заданное время

```json
{
  "version": 2,
  "requestId": "scheduled-20260808-1100",
  "destination": {
    "key": "test-group"
  },
  "content": {
    "type": "text",
    "text": "Текст отложенного сообщения"
  },
  "delivery": {
    "mode": "schedule_at",
    "scheduleAt": "2026-08-08T11:00:00+02:00",
    "timeZone": "Europe/Kaliningrad",
    "recipientInvisiblePreparation": true
  }
}
```

### Подготовить, но не отправлять

```json
{
  "version": 2,
  "requestId": "draft-20260807-001",
  "destination": {
    "exactTitle": "Тестовая группа"
  },
  "content": {
    "type": "text",
    "text": "Материал для проверки"
  },
  "delivery": {
    "mode": "stage_only",
    "stageAt": "2026-09-01T12:00:00+02:00",
    "timeZone": "Europe/Kaliningrad",
    "recipientInvisiblePreparation": true
  }
}
```

### Изображение, подпись и форматированная ссылка

```json
{
  "version": 2,
  "requestId": "rich-post-20260807-001",
  "destination": {
    "key": "test-group"
  },
  "content": {
    "type": "rich_post",
    "text": "Текст публикации",
    "image": {
      "path": "generated/max-test-post.png"
    },
    "links": [
      {
        "text": "Открыть «Полюбить Калининград»",
        "url": "https://kenigevents.ru/"
      }
    ]
  },
  "delivery": {
    "mode": "send_now",
    "timeZone": "Europe/Kaliningrad",
    "recipientInvisiblePreparation": true,
    "reuseExistingStage": true
  }
}
```

Ссылка вставляется через HTML Clipboard API. До staging проверяются видимый текст и canonical href; после commit свежий context требует, чтобы один message-container одновременно содержал подпись, media и все точные ссылки.

### Только проверка

```json
{
  "verifyOnly": true
}
```

`verifyOnly` не создаёт staged-объект и не проходит commit-point. Результат — `verified_existing` либо fail-closed ошибка.

Legacy version 1 по-прежнему читается, но нормализуется в version 2. Даже старое действие `text` теперь идёт через staging, а не через прямую отправку.

## Нужна ли LLM внутри алгоритма

В браузерном исполнительном контуре LLM не нужна и не должна использоваться. Роли элементов, заголовки, staged-list, ссылки, media и commit-point проверяются детерминированно.

LLM полезна на semantic planning layer, поскольку пользовательская формулировка может быть неполной. Когда задачу ставят текущему ассистенту, отдельная модель не требуется: контекст уже доступен ассистенту, а браузерный код получает нормализованный command envelope.

Если понадобится автономный resolver, рекомендуемая схема:

1. детерминированный поиск возвращает обезличенные candidate hints;
2. Gemini Lite через существующий общий limiter предлагает intent и поисковые варианты;
3. модель не получает cookies, `MAX_SESSION`, полный DOM и тексты посторонних чатов;
4. ответ модели не является разрешением на отправку;
5. deterministic resolver повторно требует единственного адресата;
6. при остаточной неоднозначности требуется человек.

Gemini Lite предпочтительнее Gemma для этого узкого слоя: здесь важнее понимание коротких естественных формулировок и опечаток. Подключать модель внутрь Playwright commit-path не требуется.

## Fail-closed и идемпотентность

- `MAX_SESSION` не печатается и не попадает в evidence;
- неоднозначный адресат блокирует выполнение до композера;
- текст ограничен 4000 символами;
- ссылки разрешены только по HTTPS;
- изображение проверяется до открытия чата и ограничено 20 MiB;
- содержимое вставляется атомарно;
- staged-объект должен быть найден ровно один раз;
- `Отправить сейчас` вызывается только после проверки staged-объекта;
- после commit-point результат проверяет новый browser context;
- повторный запуск сначала ищет уже опубликованный материал;
- параллельные команды сериализуются одной concurrency-группой.

`requestId` отражается в receipt, но долговечный idempotency ledger ещё не внедрён. Для массовой работы нужен отдельный private store.

## Публичный репозиторий и private command plane

Поскольку репозиторий сейчас публичный, реальные тексты, названия закрытых чатов и URL изображений нельзя коммитить в `.github/max-live-command.json`.

Для production нужен private command plane:

- workflow получает только непрозрачный `command_id`;
- payload хранится в приватном Supabase/YDB-контуре либо private repository/environment;
- payload читается однократно и после обработки помечается consumed;
- публичные Actions logs содержат только request ID, outcome и безопасные error codes.

До внедрения private command plane публичный push-trigger предназначен только для безвредных тестов. Ручной `workflow_dispatch` также не следует использовать для конфиденциального command JSON без отдельной проверки его публичной видимости.

## Evidence и удаление артефактов

В production `capture_evidence=false`. При диагностике сохраняются только:

- обрезанная рабочая область текущего чата;
- ограниченная DOM-сводка;
- JSON receipt без сессии.

GitHub retention установлен в один день, но после анализа artifacts удаляются workflow `MAX artifact cleanup`. Локальные ZIP, screenshots, DOM и временные каталоги также удаляются.

## Следующие усиления

- второй тестовый аккаунт для recipient-side notification и typing-indicator evidence;
- private destination registry и стабильные route fingerprints;
- private command queue вместо публичного JSON/push;
- долговечный idempotency ledger;
- signed media download с MIME, размером и SHA-256;
- durable receipts `accepted`, `staged`, `committed`, `verified`;
- монитор срока действия `MAX_SESSION`;
- при необходимости — read-only Gemini Lite resolver через общий limiter.
